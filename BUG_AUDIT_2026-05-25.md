# MathTS Bug & Issue Audit -- 2026-05-25

**Audit performed by:** Claude (Opus 4.7, 1M context) in /loop mode
**Methodology:** RLM-style codebase scan + HonestClaude verification
discipline (every finding has a file:line citation; speculative items
are excluded or flagged).
**Repo HEAD at audit:** `b507fb7` (release: workerpool/parallel/functions 0.2.0)
**Scope:** Active source only. Dormant mathjs-synced code (122K LOC under
functions/src and core/src) is *not* audited -- per CLAUDE.md it carries
known upstream type errors that are mathjs's responsibility.

## Executive summary

- **One security regression (S-1):** matrix's three WASM load paths skip
  the documented SHA-384 integrity check. Present in functions/ and
  assembly/ loaders; missing from all three matrix loaders.
- **One active functional bug (B-1):** functions/src/wasm/WasmLoader.ts
  references the legacy mathjs filenames mathjs-as.wasm / mathjs.wasm
  instead of mathts-as.wasm / mathts.wasm. Loader cannot find its
  artifacts; every consumer silently uses JS fallback.
- **One cross-package architectural bug (B-3):** matrix's source-relative
  WASM path resolution (../../../lib/wasm/) was correct for source-layout
  but is wrong from matrix/dist/index.js. Cross-package consumers
  (functions, expression, compat) hit the wrong path; silent JS fallback
  hides it.
- **Three skipped SVD tests (B-4):** documented limitations in full-matrix
  support, QR iteration stability, and transpose-handling for 4x6.
- **35 commits of mathjs upstream drift (B-5)** since the last sync
  (2026-04-02). Includes "fix: resolve all PR review issues -- 6 CRITICAL,
  6 HIGH". The TS split at upstream e62bcd749 blocks the existing sync
  script.
- **1 moderate dev-dependency vulnerability (B-7):** turbo < 2.9.14, two
  GHSAs. Fix available via npm audit fix. End-user packages unaffected.

Active code is in generally good shape: 638 source files, 105K LOC,
type-disciplined (only 4 `as any` total across parallel/tensor/autograd/
matrix/workbook/compat/typed-function/workerpool). The 350 `as any` and 53
`as unknown as` instances are concentrated in expression/ and core/ which
mostly mirror mathjs's loose factory typings. Security invariants for the
expression sandbox and WorkerPool timeout are intact.

## Detailed findings

### S-1 -- Matrix WASM loaders bypass SHA-384 integrity check

**Severity:** medium-high   **Confidence:** high

**Evidence.** CLAUDE.md documents the invariant:

> "WASM SHA-384 manifest verification. functions/src/wasm/WasmLoader.ts
> (Node + browser load paths) and assembly/src/bindings/wasm-loader.ts
> both hash the .wasm buffer and compare to wasm-manifest.json before
> compile/instantiate. Do not bypass, weaken to a non-cryptographic
> check, or skip on streaming compile paths."

Audit script tools/audit-2026-05-25/wasm-audit.py confirms **five** files
call WebAssembly.compile or WebAssembly.instantiate. Only two perform the
SHA-384 integrity check:

| File | SHA-384 check | Notes |
|------|---------------|-------|
| functions/src/wasm/WasmLoader.ts:1006 | **yes** (verifyWasmIntegrity) | matches invariant |
| assembly/src/bindings/wasm-loader.ts:186 | **yes** (verifyWasm) | matches invariant |
| matrix/src/backends/WasmLoader.ts:776-784 | **no** | readFile then compile directly |
| matrix/src/backends/WASMBackend.ts:407-413 | **no** | readFile then compile directly |
| matrix/src/backends/wasm/detect.ts | **no** | feature-detection only |

**Impact.** A tampered .wasm artifact would load without detection on
every matrix code path. @danielsimonjr/mathts-matrix is published and
depended on by @danielsimonjr/mathts-functions and
@danielsimonjr/mathts-compat -- so the exposure surface is end-users, not
just dev environments.

**Recommendation.** Port the verifyWasmIntegrity pattern from
functions/src/wasm/WasmLoader.ts. The browser streaming path needs the
same buffer-materialization treatment used in
functions/src/wasm/WasmLoader.ts:1027-1042 (refuse streaming when a
manifest is present, because streaming bypasses integrity checks). Add a
regression test analogous to
functions/tests/security/wasm-integrity.test.ts. CLAUDE.md text should
also be updated -- it currently names only the two verified loaders,
which contributed to this regression being missed.

### B-1 -- functions/src/wasm/WasmLoader.ts uses legacy mathjs filenames

**Severity:** high   **Confidence:** high

**Evidence.** functions/src/wasm/WasmLoader.ts:983-993 (paraphrased --
see the file for the exact code):

- Node branch returns './lib/wasm/mathjs-as.wasm' or
  './lib/wasm/mathjs.wasm'
- Browser branch builds new URL('../../lib/wasm/mathjs-as.wasm', ...).href
- Env-var name checked is MATHJS_WASM_BACKEND

The actual artifacts (per lib/wasm/wasm-manifest.json) are mathts-as.wasm
and mathts.wasm -- these filenames pre-date the mathjs-to-MathTS rebrand.

The env-var name (MATHJS_WASM_BACKEND) is also legacy and likely
shadowed by the post-rename MATHTS_BACKEND used in
matrix/src/backends/WasmLoader.ts:752.

**Consumers** (confirmed via grep):
functions/src/typed/{numeric,geometry,signal}.ts import wasmLoader from
this file and call wasmLoader.getModule(). Because the load always fails
(file not found), getModule() returns null and every consumer falls back
to JS -- silently, with no console.warn on this code path.

**Impact.** Every release of @danielsimonjr/mathts-functions (current
0.2.0, just published) ships with the WASM path for typed/numeric,
typed/geometry, and typed/signal unreachable. The WASM artifacts are
also not bundled into the functions npm tarball, so even fixing the
filenames would also require shipping the artifacts (separate issue).

**Recommendation.** Rename mathjs-as.wasm to mathts-as.wasm and
mathjs.wasm to mathts.wasm in both branches of getDefaultWasmPath;
rename the env variable to MATHTS_BACKEND (or accept both for one
release).

### B-2 -- functions/src/wasm/WasmLoader.ts uses CWD-relative Node path

**Severity:** medium   **Confidence:** high

**Evidence.** Same code block as B-1, line 988 returns a
'./lib/wasm/...' literal string for the Node branch. './lib/wasm/...' is
resolved against process.cwd(), not against the file's own location.
Only works when Node is launched from the repo root.

This is the same pattern that matrix/src/backends/WasmLoader.ts already
moved away from (per its 2026-05-22 fix, recorded in CHANGELOG.md:713:
"matrix WasmLoader CWD-relative default path").

**Impact.** Once B-1 is fixed and filenames are correct, this
CWD-relative path will then fail for anyone running tests from a
subdirectory or running binaries via a globally-installed CLI.

**Recommendation.** Use the same
fileURLToPath(new URL(..., import.meta.url)) pattern as
matrix/src/backends/WasmLoader.ts:765-771 (introduced in commit 3d218f5).

### B-3 -- Cross-package WASM resolution: src-hop count is wrong from dist

**Severity:** medium   **Confidence:** high

**Evidence.** matrix/src/backends/WasmLoader.ts:758 and
WASMBackend.ts:374 both resolve the WASM URL
with 3 `../` hops relative to import.meta.url. Correct from source
(matrix/src/backends/foo.ts -> matrix/src/ -> matrix/ -> <repo>) but
wrong from dist (matrix/dist/index.js -> matrix/ -> <repo> -> <parent>).

matrix's own tests run against src (so they pass). Cross-package
consumers (functions, expression, compat) import matrix's dist via the
workspace -- those tests emit a path with the Mathts segment missing and
silently fall back to JS. matrix/dist/ is what npm publishes -- so this
affects every consumer.

**Impact.** End-users of @danielsimonjr/mathts-matrix who consume it
from another package (the documented usage pattern) never get WASM
acceleration on Node, only the JS fallback.

**Recommendation.** Two viable approaches:

1. **Build-time asset copy.** Add a tsup onSuccess hook that copies
   lib/wasm/*.wasm into matrix/dist/wasm/. Then change the loader to use
   ./wasm/${wasmFile} relative to import.meta.url. Works identically
   from source and dist, and ships the artifacts in the npm tarball --
   also a precondition for B-1 to actually produce WASM speedups for
   end-users.
2. **Runtime fallback candidates.** Try a 2-hop path first, then 3-hop,
   return whichever exists. Cheaper to implement; lib/wasm still not
   shipped to npm consumers without separate work.

(1) is the canonical npm-package answer.

### B-4 -- Three SVD test cases marked it.skip document real failures

**Severity:** medium   **Confidence:** high

**Evidence.** matrix/tests/decomposition/svd.test.ts:

| Line | Test name | Skip reason |
|------|-----------|-------------|
| 180 | should satisfy A = U*S*V' for tall matrix | requires full matrix support |
| 461 | should handle 5x5 matrix | numerical stability issue in QR iteration |
| 480 | should handle 4x6 matrix | dimension mismatch in transpose handling |

describe.skip at matrix/tests/gpu/operations.test.ts:294 is a legitimate
environment guard (WebGPU requires a browser) and is **not** included
here.

**Impact.** SVD is exposed via @danielsimonjr/mathts-matrix. Users
calling svd on a non-square (tall) matrix, a 5x5 matrix where QR doesn't
converge, or a 4x6 matrix will get a wrong answer or thrown error.
Existing tests catch the cases that do work; the broken cases are
silenced.

**Recommendation.** Address each case on its own merit. Each fix should
remove .skip and add a regression test with a fixed input.

### B-6 -- wasm-manifest.json drifts on WASM rebuild

**Severity:** low   **Confidence:** high

**Evidence.** Rebuilding the WASM binary produces a
lib/wasm/mathts-as.wasm whose SHA-384 hash differs from the value in
lib/wasm/wasm-manifest.json:

    Rebuilt SHA-384:   sha384-mgOSQf/ADGeU6bzcaw3rfiLlFx1OjiaHVXCf9jGitcnZCP7SfXGBhASaLZVULUDQ
    Committed:         sha384-Z4jA2gB2FqAFzenekFZvSF2MozAtueJgdh5OkELU/3zIe5iVZ2bSRlmztbYXOc6u

The build does not invoke tools/generate-wasm-manifest.mjs after
producing the binary. Recent commit dc5c050 ("fix(wasm): regenerate
manifest after Slice 6.3 + 6.4 combined rebuild") suggests this is a
known operational gotcha that hits on every rebuild.

**Impact.** Dev-only: any developer rebuilding the WASM artifact
ends up with a binary that fails the SHA-384 check on next test run.
Doesn't affect end-users.

**Recommendation.** Have the WASM build invoke
tools/generate-wasm-manifest.mjs automatically as its final step, OR add
a git pre-commit hook to fail if lib/wasm/*.wasm changed without
regenerating the manifest.

### H-2 (historical, fixed in this session) -- Windows doubled-drive WASM path

**Status:** fixed in commit 3d218f5.
Three matrix loaders used URL.pathname to derive the on-disk path. On
Windows that returns /C:/foo/bar.wasm, which fs.readFile resolves
drive-relative. All three now use fileURLToPath.
