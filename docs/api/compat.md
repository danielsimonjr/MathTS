# @danielsimonjr/mathts-compat API Reference

mathjs compatibility layer for easy migration.

> For the complete, always-current list of every export, see the
> [Complete export index](#complete-export-index) below (generated by
> `npm run docs:functions`, drift-checked in `docs:functions:check`).

## Installation

```bash
npm install @danielsimonjr/mathts-compat
```

## Overview

The compat package provides a mathjs-compatible API, allowing drop-in replacement:

```typescript
// Before (mathjs)
import { create, all } from 'mathjs';
const math = create(all);

// After (MathTS)
import { create, all } from '@danielsimonjr/mathts-compat';
const math = create(all);

// Same API works
math.add(1, 2);
math.complex(3, 4);
math.matrix([
  [1, 2],
  [3, 4],
]);
```

## create(all)

Creates a math instance with all functions.

```typescript
import { create, all } from '@danielsimonjr/mathts-compat';

const math = create(all);
```

### Configuration

Per-instance settings do **not** mutate the shared `@danielsimonjr/mathts-functions`
singleton. Barrel `evaluate` / `config()` stay on the process default unless you call
`config({ … })` on the functions package directly.

```typescript
import { create, all } from '@danielsimonjr/mathts-compat';
import { evaluate, config as fnConfig } from '@danielsimonjr/mathts-functions';

const a = create(all, { number: 'BigNumber' });
const b = create(all, { number: 'Fraction' });

a.evaluate('e ^ 2'); // BigNumber
b.evaluate('1/2'); // Fraction
evaluate('e ^ 2'); // number — unchanged barrel
fnConfig().number; // 'number'

a.config({ precision: 128, matrix: 'Array' });
a.config().precision; // 128
b.config().precision; // not 128
```

```typescript
const math = create(all, {
  precision: 64, // BigNumber precision
  matrix: 'Matrix', // 'Matrix' or 'Array'
  number: 'number', // 'number' | 'BigNumber' | 'Fraction'
  epsilon: 1e-12, // Floating point tolerance (instance mirror only)
});

math.config({ precision: 128 });
```

### `eigs` (#1561)

On `create(all)`, `eigs` is the mathjs 15.3.0 factory (precision options, non-unit eigenvector scale, magnitude-ordered values). The native `@danielsimonjr/mathts-functions` export keeps the corrected orthes/hqr2 solver with unit-normalized vectors and ignores a numeric-only `precision` knob. The factory port lives in `compat/src/mathjs-eigs/` (compat-only; not a critical-library change).

### `schur`, `sylvester`, `lyap` and `solveODE` (#1553, #1584)

On `create(all)` these four run the mathjs 15.3.0 algorithms through adapters in
`compat/src/mathjs-parity-g05.ts` (compat-only; the critical libraries keep their
own implementations):

- `schur` is mathjs's unshifted QR iteration (`qr`, then `R·Q`, until the L2 norm
  of the step drops to `1e-4`). That fixes the diagonal ordering (#1584: the
  largest eigenvalue of the 2×2 test matrix sits at `T[0][0]`) and keeps the
  subdiagonal residue the oracle leaves (`5.147e-118`, not an exact `0`). It also
  accepts BigNumber matrices (#1553): every step runs on the entries, so a
  BigNumber input returns BigNumber entries.
- `sylvester` and `lyap` are the activated factories of
  `@danielsimonjr/mathts-functions` (ports of the mathjs factories) wired to that
  `schur`, so BigNumber matrices flow through and match the oracle (#1553).
- `solveODE` is a port of the mathjs adaptive Runge-Kutta factory; its initial
  step is `(tEnd - tStart) / 1` unless `firstStep` is given (#1584).

Native MathTS differences (import the names from
`@danielsimonjr/mathts-functions` / `@danielsimonjr/mathts-matrix` to keep them):

- `schur` uses the Francis double-shift QR (`matrixSchur`), a different and more
  accurate decomposition: eigenvalues agree, but the diagonal order differs
  (smallest first for the 2×2 test matrix) and the subdiagonal is flushed to an
  exact `0`. The reconstruction `A = U·T·Uᵀ` holds in both.
- `solveODE` uses a scipy-style step control (BDF, Radau, RK23/RK45 with
  normalized error control). Both solve the issue's problem within the default
  tolerance; the step grids differ.
- BigNumber `schur` convergence uses mathjs 15.3.0's `_matrixNormTwo` stopping
  rule (Jacobi `eigs` with lexicographic `<` on `abs` when sorting eigenvalues),
  not the corrected MathTS `norm`/`eigs` ordering. The adapter computes that
  2-norm in-tree via `createRealSymmetric({ lexicographicAbsSort: true })` in
  `compat/src/mathjs-eigs/realSymmetric.ts`. A native
  `@danielsimonjr/mathts-matrix` `DenseMatrix` argument to `schur` runs the same
  mathjs QR iteration as array input (not the native Francis path). Complex
  matrices use the same in-tree Householder QR / Schur loop (no `mathjs`
  runtime import).

### Fraction formatting (#1579, #1586)

On the compat instance, `format(fraction(2))` is `"2/1"` (the same `n/1` form inside arrays,
dense and sparse matrices, and Fraction unit magnitudes), `string(fraction(1, 3))` is `"0.(3)"`
(repeating/terminating caps match mathjs 15.3.0 / fraction.js; collections map element-wise),
`print('x=$x', { x: fraction(2) })` interpolates `"x=2/1"`, and
`print(fraction(2))` throws the same `TypeError` wording as mathjs. With
`number: 'Fraction'`, `parse('1/3 + 1/4').toString()` is `"1/1 / 3/1 + 1/1 / 4/1"`;
`evaluate('1/3 + 1/4')` stays the Fraction `7/12`. Native `@danielsimonjr/mathts-core` and
`@danielsimonjr/mathts-expression` output is unchanged — only the compat wrappers differ.

## Examples

### Basic Usage

```typescript
import { create, all } from '@danielsimonjr/mathts-compat';

const math = create(all);

// Arithmetic
console.log(math.add(1, 2)); // 3
console.log(math.multiply(3, 4)); // 12
console.log(math.pow(2, 10)); // 1024

// Complex numbers
const z = math.complex(3, 4);
console.log(math.abs(z)); // 5
console.log(math.conj(z)); // Complex(3, -4)

// Matrices
const A = math.matrix([
  [1, 2],
  [3, 4],
]);
const B = math.identity(2);
console.log(math.det(A)); // -2
console.log(math.transpose(A)); // [[1,3],[2,4]]
```

### Migration Pattern

```typescript
// Step 1: Replace import
// import { create, all } from 'mathjs';
import { create, all } from '@danielsimonjr/mathts-compat';

// Step 2: Your existing code works
const math = create(all);

function calculateEigenvalues(matrix) {
  const A = math.matrix(matrix);
  // ... existing code
}

// Step 3: Gradually adopt native API where needed
import { computePool } from '@danielsimonjr/mathts-parallel';

async function parallelSum(data) {
  await computePool.initialize();
  return computePool.sum(new Float64Array(data));
}
```

## Unit equality and ordering (#1552)

`create(all)` routes **Unit–Unit** comparisons for `equal`, `unequal`, `equalScalar`,
`deepEqual`, `compare`, `larger`, `smaller`, `largerEq`, and `smallerEq` through thin
adapters in `compat/src/unit-relational.ts`. They delegate to the activated mathjs
factories in `@danielsimonjr/mathts-functions` so results match mathjs 15.3.0 (for
example `50cm == 0.5m` under `number: 'BigNumber'`, dimension mismatches throw
`Cannot compare units with different base`, and `deepEqual` of two Units follows
mathjs’s `valueOf` + `equal` path). Affine temperatures on the compat instance follow
mathjs (`0 degC == 32 degF` is `false`). Native `functions` / `core` `equal` compares
absolute SI, so those two temperatures are equal. `min`/`max`/`sign` of Units on the
compat instance also use the factories. Expression evaluation uses the same instance
methods via the expression scope.

Integral Fraction values shown by `format` use an `n/1` suffix on the compat instance
(`format-parity.ts`) so compare results such as `Fraction 1/1` match the oracle; full
Fraction formatting parity is #1579 (G15).

## API Differences from mathjs

| mathjs                         | @danielsimonjr/mathts-compat                      |
| ------------------------------ | ------------------------------------------------- |
| `math.bignumber(x).toNumber()` | `math.bignumber(x).toNumber()` (also `valueOf()`) |
| `m.get([row, col])`            | `m.get(row, col)`                                 |
| `m.size()`                     | `math.size(m)` returns `[rows, cols]`             |
| `f.n`, `f.d`                   | `f.numerator`, `f.denominator` (bigint)           |

**`Complex` non-finite arithmetic and `zpk2tf` (#1589):** on `create(all)` only, compat matches mathjs 15.3.0 complex.js rules (NaN parts count as infinite in `add`/`subtract`/`multiply`/`divide`/`dotMultiply`; compat `zpk2tf`/`freqz` use the same arithmetic). Native MathTS `Complex` elsewhere keeps IEEE semantics. The 2-D Matrix `zpk2tf` repro above matches the oracle; 1-D results unchanged. Compat `zpk2tf` gain: `number | bigint | string | boolean` only (not BigNumber or Fraction).

See [Migration Guide](../migration/guide.md) for complete details.

## Native MathTS differences (compat matches mathjs)

`create(all)` on `@danielsimonjr/mathts-compat` matches mathjs 15.3.0 for
`zeta`, `symbolicEqual`, and `range` (including mathjs quirks), via adapters in
`compat/src/mathjs-parity-1585.ts`. Importing the same names from
`@danielsimonjr/mathts-functions` keeps the more accurate MathTS behavior.
Pinned by `compat/tests/parity/g18-parity.test.ts`. (#1585)

### `zeta(-3)`

Compat matches mathjs `0.0083333345772996`. Native MathTS returns
`0.0083333333333335`, much closer to the exact value `1/120`.

### `zeta(complex(1, 2))`

Compat matches mathjs `NaN + NaNi` on the line `Re(s) = 1`. Native MathTS
returns a finite value on the critical strip (for example `zeta(0.5 + 2i)` is
finite in both libraries; only `zeta(1 + 2i)` is NaN in mathjs).

### `zeta(bignumber(4))`

Compat matches mathjs `1.0823232498396`. Native MathTS returns
`1.0823232337111`, closer to π⁴/90.

### `bernoulli`

The compat surface routes every Bernoulli index type (number, bigint, Fraction,
BigNumber, and values from `evaluate` under `config.number`) through the same
mathjs 15.3.0 recurrence as the oracle, including early returns for `0`, `1`,
and odd indexes and float overflow to `±Infinity` / `NaN` at large even indexes.
Fraction / BigNumber / Complex scalar paths follow #1554 compat adapters.

### `pinv`

Number-only dense and sparse Array / Matrix inputs use the mathjs factory
rank-factorization path (compat adapter), so singular cases such as
`pinv([[0, 1]])` and `pinv(sparse([[0, 1]]))` throw
`Cannot calculate inverse, determinant is zero` like mathjs. Non-number matrix
entries still delegate to the native typed `pinv` (generic arithmetic). Scalar
BigNumber / Fraction / Complex paths are compat adapters (#1554).

### `symbolicEqual`

Compat uses mathjs’s simplify-only equality (no exact-polynomial shortcuts).
Native MathTS also proves many polynomial identities that mathjs rejects (for
example `(x+y)^2` versus `x^2+2*x*y+y^2` in default number mode). In BigNumber
config, compat matches mathjs’s `false` for `symbolicEqual("x*y", "y*x")`.

### `range`

Under `number: 'BigNumber'`, compat matches mathjs: `range('4:10')` and
`evaluate('range("4:10")')` return `[4,…,9]`, and the string form ignores
`includeEnd` (mathjs passes it to `_out`, not `_range`). Native MathTS range
honours `includeEnd` on those paths.
