# Function Reference

All functions are exported from `@danielsimonjr/mathts-functions`.

```typescript
import { add, sin, parallelFFT, det, integrate } from '@danielsimonjr/mathts-functions';
```

This package exposes functions from **two layers**:

- **Typed layer** — native parallel-first implementations using typed-function
  dispatch. Support `number`, `bigint`, `Complex`, `Fraction`, `BigNumber`,
  `Unit`, `Dual` (forward-mode autodiff), and `Float64Array` where applicable.
  `Float64Array` inputs run in parallel worker threads and return a `Promise`.
- **Factory layer** — functions synced from mathjs and activated through the
  factory system (`det`, `inv`, `eigs`, set operations, units, sparse linear
  algebra, expression nodes, etc.). The numeric `det`/`inv` route large matrices
  through the native Float64Array LU for a large speedup.

Where a name exists in both layers (`add`, `multiply`, `sin`, …) the typed
implementation is the public export; the factory version is also exported under
a `factory_` prefix (`factory_add`, …).

**Coverage**: 668 callable functions across the typed and factory layers (744
total exports, incl. 52 CODATA physical constants — see
[Physical Constants](#physical-constants) — and 9 type-conversion functions). The
complete, always-current export list is the [export index](#complete-export-index)
at the end of this page, generated by `npm run docs:functions`. Remaining coverage
gaps are tracked in
[`docs/roadmap/GAP_ANALYSIS_BRIDGES_AND_MATH_FUNCTIONS.md`](../roadmap/GAP_ANALYSIS_BRIDGES_AND_MATH_FUNCTIONS.md).

**Automatic differentiation**: forward-mode AD over the plain functions surface
via the `Dual` number type — `derivativeAt((x) => multiply(sin(x), x), 2)`
differentiates any expression built from the overloaded elementary functions
exactly (see `derivativeAt` / `valueAndDerivativeAt` / `gradientAt`). For
reverse-mode / tensor gradients, see `@danielsimonjr/mathts-autograd`.

Function tables in hardware-accelerated categories carry an **Accel** column:

- **`parallel`** — the function's `Float64Array` (or large-matrix) path is
  dispatched across worker threads by the compute pool.
- **`WASM`** — the function has a WebAssembly fast path for large inputs.
- **`WebGPU`** — the function runs on the GPU via WebGPU compute shaders for
  large inputs (32-bit float precision).

Each acceleration falls back automatically to a pure-TypeScript implementation
when the input is small, the worker pool is not initialized, or the WASM /
WebGPU device is unavailable.

Every category below is documented in three parts: **Details** — supported
types, return semantics, and numerical caveats; **Background & History** — the
underlying mathematics and where it originates; and **Examples** — runnable
code. A browsable HTML edition of this page is available at
[`functions.html`](./functions.html).

The factory layer additionally provides scalar variants used internally and by
the expression evaluator: `addScalar`, `subtractScalar`, `multiplyScalar`,
`divideScalar`, `dotMultiply`, `dotDivide`, `dotPow`, `invmod`, `nthRoots`.

### Details

- Operators dispatch polymorphically through typed-function; mixed-type
  arguments promote to the widest type (`number + Complex → Complex`,
  `number + Fraction → Fraction`).
- `Float64Array` arguments are processed in parallel worker threads and return a
  `ParallelResult<Float64Array>` — unwrap the array with `.result`.
- `add` and `multiply` on a `DenseMatrix` perform matrix algebra (the matrix
  product, not the element-wise product). Use `dotMultiply` / `dotDivide` /
  `dotPow` for element-wise operations.
- `pow` with a negative base and a fractional exponent returns a `Complex`;
  `sqrt`, `cbrt`, and `log` of negative reals likewise return `Complex` when the
  input type allows it.
- `expm1` and `log1p` preserve precision for arguments near zero, where
  `exp(x) - 1` and `log(1 + x)` lose significant digits to cancellation.
- `mod` returns a result with the sign of the divisor (true mathematical
  modulo), unlike the JavaScript `%` operator.
- `round`, `floor`, `ceil`, and `fix` accept an optional digit count;
  `fix` truncates toward zero.

### Background & History

The arithmetic layer generalises the four elementary operations to every MathTS
numeric type. `gcd`, `lcm`, and `xgcd` derive from the Euclidean algorithm,
described in Euclid's _Elements_ (c. 300 BCE) and still one of the oldest
algorithms in continuous use; `xgcd` returns the Bézout coefficients that make
modular inverses and the Chinese Remainder Theorem possible. The
cancellation-safe pair `expm1` / `log1p` comes from IEEE-754 numerical-analysis
practice and is standard in the C math library for exactly the precision reasons
above.

### Examples

```typescript
import { add, pow, log, mod } from '@danielsimonjr/mathts-functions';
import { Complex, Fraction } from '@danielsimonjr/mathts-core';

add(1, 2); // 3
add(new Fraction(1n, 3n), new Fraction(1n, 6n)); // Fraction(1, 2)
pow(new Complex(0, 1), 2); // Complex(-1, 0)
log(100, 10); // 2
mod(17, 5); // 2
```

## Relational & Comparison

| Function               | Description                         | Accel |
| ---------------------- | ----------------------------------- | ----- |
| `equal(a, b)`          | Equality test                       | —     |
| `unequal(a, b)`        | Inequality test                     | —     |
| `smaller(a, b)`        | `a < b`                             | —     |
| `smallerEq(a, b)`      | `a ≤ b`                             | —     |
| `larger(a, b)`         | `a > b`                             | —     |
| `largerEq(a, b)`       | `a ≥ b`                             | —     |
| `compare(a, b)`        | Three-way compare → -1, 0, 1        | —     |
| `compareNatural(a, b)` | Natural ordering across mixed types | —     |
| `compareText(a, b)`    | Lexical string comparison           | —     |
| `equalScalar(a, b)`    | Scalar equality                     | —     |
| `equalText(a, b)`      | String equality                     | —     |
| `deepEqual(a, b)`      | Element-wise deep equality          | —     |

### Details

- The `equal`/`unequal`/`smaller`/`larger` family return booleans; `compare`
  returns `-1`, `0`, or `1`.
- Numeric comparisons apply a configurable tolerance (`epsilon`) so that results
  differing only by rounding error compare as equal — exact equality is rarely
  meaningful for floating-point values.
- `compareNatural` defines a deterministic total order across mixed types and is
  used as the canonical sort key by symbolic simplification and set operations.
- `compareText` and `equalText` operate on raw strings with no numeric coercion.
- `deepEqual` recurses into matrices and nested arrays, comparing element by
  element.
- All twelve ops dispatch typed-only (no `parallel`/`WASM`/`WebGPU` tier).
  Per-element comparison cost is too low for worker marshaling to be a net win;
  bulk-array comparison use-cases that genuinely benefit from parallel routing
  are tracked as a deferred Tier-3 slice (see
  [`docs/roadmap/FUNCTION_GAPS_AUDIT.md`](../roadmap/FUNCTION_GAPS_AUDIT.md)).

### Background & History

Order and equality relations are foundational to mathematics, but their
_computational_ treatment must contend with the fact that floating-point
arithmetic is inexact. Tolerant comparison — testing whether two values agree to
within a relative/absolute epsilon — is the pragmatic answer adopted across
numerical software. `compareNatural` additionally supplies a stable canonical
ordering, which is what allows a computer-algebra system to put an expression
into a unique normal form regardless of how it was entered.

### Examples

```typescript
import { equal, smaller, compare, deepEqual } from '@danielsimonjr/mathts-functions';

equal(0.1 + 0.2, 0.3); // true   (tolerant comparison)
smaller(3, 5); // true
compare(2, 2); // 0
deepEqual([1, 2, 3], [1, 2, 3]); // true
```

## Trigonometry

Functions support `number`, `Complex`, `BigNumber`, and parallel `Float64Array`.

| Function                         | Description                                      | Accel    |
| -------------------------------- | ------------------------------------------------ | -------- |
| `sin(x)` `cos(x)` `tan(x)`       | Sine, cosine, tangent                            | parallel |
| `csc(x)` `sec(x)` `cot(x)`       | Cosecant, secant, cotangent                      | parallel |
| `asin(x)` `acos(x)` `atan(x)`    | Inverse sine, cosine, tangent                    | parallel |
| `atan2(y, x)`                    | Two-argument arctangent                          | —        |
| `acsc(x)` `asec(x)` `acot(x)`    | Inverse cosecant, secant, cotangent              | —        |
| `sinh(x)` `cosh(x)` `tanh(x)`    | Hyperbolic sine, cosine, tangent                 | parallel |
| `asinh(x)` `acosh(x)` `atanh(x)` | Inverse hyperbolic sine, cosine, tangent         | parallel |
| `csch(x)` `sech(x)` `coth(x)`    | Hyperbolic cosecant, secant, cotangent (factory) | —        |
| `acsch(x)` `asech(x)` `acoth(x)` | Inverse hyperbolic csc/sec/cot (factory)         | —        |
| `toRadians(deg)`                 | Convert degrees to radians                       | —        |
| `toDegrees(rad)`                 | Convert radians to degrees                       | —        |
| `hypot(a, b, …)`                 | Hypotenuse `sqrt(Σ xᵢ²)`                         | —        |

### Details

- All arguments and results are in **radians**; convert with `toRadians` and
  `toDegrees`.
- Reciprocal functions (`csc`, `sec`, `cot`) and their hyperbolic counterparts
  diverge at their poles and return `Infinity` or `NaN` there.
- `atan2(y, x)` resolves the correct quadrant from the signs of both arguments;
  its range is `(-π, π]`.
- `hypot` is overflow-safe — it scales by the largest term so that
  `hypot(1e200, 1e200)` does not overflow.
- Inverse functions return principal values; over `Complex` arguments they
  follow the conventional branch cuts.

### Background & History

Trigonometry grew out of Hellenistic astronomy: Hipparchus compiled the first
chord tables around 140 BCE, and the sine function itself reached its modern
form through Indian (Aryabhata) and Islamic (al-Battani, Abu al-Wafa)
mathematicians. The hyperbolic functions are far younger — introduced by
Vincenzo Riccati and Johann Lambert in the 1760s. Euler's formula
`e^(ix) = cos x + i·sin x` unifies the circular and hyperbolic families with the
exponential function, which is precisely why MathTS can evaluate every one of
them directly over `Complex` arguments.

### Examples

```typescript
import { sin, cos, toDegrees } from '@danielsimonjr/mathts-functions';
import { Complex } from '@danielsimonjr/mathts-core';

sin(Math.PI / 6); // 0.5
cos(new Complex(0, 1)); // Complex(cosh(1), 0) ≈ Complex(1.543, 0)

const angles = new Float64Array([0, Math.PI / 6, Math.PI / 4, Math.PI / 3, Math.PI / 2]);
const sines = await sin(angles); // parallel → Float64Array

toDegrees(Math.PI); // 180
```

## Logical & Bitwise

### Bitwise

| Function                | Description                              | Types                                 | Accel                   |
| ----------------------- | ---------------------------------------- | ------------------------------------- | ----------------------- |
| `bitAnd(a, b)`          | Bitwise AND                              | number, bigint, BigNumber, Int32Array | parallel + WASM (≥65 K) |
| `bitOr(a, b)`           | Bitwise OR                               | number, bigint, BigNumber, Int32Array | parallel + WASM (≥65 K) |
| `bitXor(a, b)`          | Bitwise XOR                              | number, bigint, BigNumber, Int32Array | parallel + WASM (≥65 K) |
| `bitNot(x)`             | Bitwise NOT (unary)                      | number, bigint, BigNumber, Int32Array | parallel + WASM (≥65 K) |
| `leftShift(x, n)`       | Bitwise left shift                       | number, bigint, BigNumber, Int32Array | parallel + WASM (≥65 K) |
| `rightArithShift(x, n)` | Arithmetic (sign-preserving) right shift | number, bigint, BigNumber, Int32Array | parallel + WASM (≥65 K) |
| `rightLogShift(x, n)`   | Logical (zero-filling) right shift       | number, bigint, BigNumber, Int32Array | parallel + WASM (≥65 K) |

`Int32Array` operands are processed in parallel worker threads via `ComputePool`.
Above the threshold `WASM_BITWISE_THRESHOLD = 65,536` elements, a WASM kernel is
used instead of the worker-pool path. Scalar (`number`, `bigint`, `BigNumber`)
inputs run synchronously with no dispatch overhead. Shift operations also accept
`(Int32Array, number)` for a scalar shift count.

### Logical

| Function        | Description                                            | Types                                    | Accel |
| --------------- | ------------------------------------------------------ | ---------------------------------------- | ----- |
| `and(a, b)`     | Logical AND — true when both operands are truthy       | any, number, bigint, BigNumber, Complex  | —     |
| `or(a, b)`      | Logical OR — true when at least one operand is truthy  | any, number, bigint, BigNumber, Complex  | —     |
| `xor(a, b)`     | Logical XOR — true when exactly one operand is truthy  | any, number, bigint, BigNumber, Complex  | —     |
| `not(x)`        | Logical NOT — flips truthiness                         | any, number, bigint, BigNumber, Complex  | —     |
| `nullish(a, b)` | Returns `a` unless `a` is `null`/`undefined`, else `b` | any (returns one operand, not a boolean) | —     |

Truthiness rules: `number` — non-zero and non-NaN; `bigint` — non-zero;
`BigNumber` — non-zero and non-NaN; `Complex` — `re !== 0 || im !== 0`.
All operators accept a variadic third+ argument. `nullish` is unlike `or` — a
value of `0`, `false`, or `''` is **not** considered nullish.

### Details

- Bitwise operators (`bitAnd`, `bitOr`, `bitXor`, `bitNot`, `leftShift`,
  `rightArithShift`, `rightLogShift`) act on 32-bit two's-complement integers for
  `number` inputs and on arbitrary-width values for `bigint` inputs; `BigNumber`
  operands must be finite integers.
- `rightArithShift` preserves the sign bit (sign extension); `rightLogShift`
  zero-fills from the left.
- Logical operators (`and`, `or`, `xor`, `not`) coerce their operands to boolean
  using the truthiness rules above; `not` returns a boolean.
- `nullish` returns `a` unless `a` is `null` or `undefined`, in which case it
  returns `b`.

### Background & History

Boolean algebra was formalised by George Boole in _An Investigation of the Laws
of Thought_ (1854) and became the mathematical basis of digital logic through
Claude Shannon's 1937 master's thesis. The bitwise operators mirror the
instruction set of real hardware and remain essential for masks, flags, packed
data, and fixed-point arithmetic. MathTS extends them to `bigint`, lifting the
32-bit ceiling for cryptographic and number-theoretic work.

### Examples

```typescript
import { and, xor, bitAnd, leftShift } from '@danielsimonjr/mathts-functions';

and(true, false); // false
xor(1, 0); // true
bitAnd(12, 10); // 8     (1100 & 1010 = 1000)
leftShift(1, 4); // 16
```

| `lambertW(x[, branch])`                     | Lambert W function                           | parallel               |
| `chebyshevT(n, x)`                          | Chebyshev polynomial (first kind)            | parallel               |
| `hermiteH(n, x)`                            | Hermite polynomial                           | parallel               |
| `laguerreL(n, x)`                           | Laguerre polynomial                          | parallel               |
| `legendreP(n, x)`                           | Legendre polynomial                          | parallel               |
| `zeta(s)`                                   | Riemann zeta function (factory layer)        | —                      |

### Details

- The gamma family is evaluated with the Lanczos approximation; use `lgamma`
  (log-gamma) for large arguments where `gamma` itself would overflow.
  `digamma` is the logarithmic derivative `d/dx ln Γ(x)`.
- `betainc` and `gammainc` / `gammaincp` return _regularized_ (normalised to
  `[0, 1]`) incomplete functions — the building blocks of the Beta, Gamma, t,
  F, and chi-squared cumulative distributions.
- Bessel functions of the second kind (`besselY*`) and `besselK` require
  `x > 0`; the orthogonal polynomials `chebyshevT`, `hermiteH`, `laguerreL`,
  and `legendreP` are evaluated by stable three-term recurrences.
- `ellipticK(m)` and `ellipticE(m)` take the **parameter** `m = k²`, not the
  modulus `k`.
- `lambertW` solves `w·e^w = x`; pass `branch = 0` for the principal branch
  (default) or `branch = -1` for the lower real branch on `[-1/e, 0)`.
- **WASM acceleration:** `besselJ0` / `besselJ1` / `besselJ(n, x)`,
  `besselY0` / `besselY1` / `besselY(n, x)`, `airyAi` / `airyBi`,
  `ellipticK` / `ellipticE` / `ellipticF` / `ellipticEIncomplete` /
  `ellipticPi`, `carlsonRC/RD/RF/RJ`, and `lgamma` route to AssemblyScript
  WASM kernels for `Float64Array` inputs of length ≥ 1024
  (`WASM_SPECIAL_THRESHOLD`); the `functions` package bundles the wasm and
  resolves it package-relative, so the path is live. Bessel J/Y use an
  ascending series for `|x| ≤ 13` and the Hankel asymptotic above; `besselJ(n,x)`
  uses upward recurrence for `n < x` and Miller's backward recurrence otherwise.
  `airyAi` / `airyBi` use the convergent series for `|x| ≤ 5` and the asymptotic
  expansion (DLMF §9.7, coefficients generated by the §9.7.2 recurrence) beyond.
  WASM and JS paths share these algorithms and agree to **<1e-9** (validated vs
  mpmath: `functions/tests/diff-special.test.mjs`).

### Background & History

Special functions are the named solutions that recur across physics and
analysis. Euler introduced the gamma function in 1729 to interpolate the
factorial; Daniel Bernoulli and Friedrich Bessel studied the Bessel functions
(1817) while solving cylindrical wave and heat problems. The error function
quantifies Gaussian probability and diffusion; elliptic integrals — studied by
Legendre, Abel, and Jacobi — measure the arc length of an ellipse and the period
of a pendulum. The Lambert W function dates to a 1758 paper by J. H. Lambert but
acquired its name and modern prominence only in the 1990s through the Maple
computer-algebra system.

### Examples

```typescript
import { erfc, beta, gammainc, besselJ0, lambertW } from '@danielsimonjr/mathts-functions';

erfc(1); // ~0.1573
beta(0.5, 0.5); // pi
gammainc(1, 1); // ~0.6321 (= 1 - 1/e)
besselJ0(0); // 1
lambertW(1); // ~0.5671 (omega constant)
```

  arguments; large arguments are evaluated through the gamma / log-gamma
  functions and become floating-point approximations.
- `fibonacci` uses the O(log n) fast-doubling identity rather than naive
  iteration; `catalan`, `bellNumbers`, `stirlingS2`, and `bernoulli` are exact
  for integer arguments.
- `prime`, `nextPrime`, `primePi`, and `primeFactors` use trial division and
  sieving — practical for moderate inputs, not industrial-scale factorisation.
- `eulerPhi`, `divisorSigma`, `moebiusMu`, and `carmichaelLambda` are
  multiplicative arithmetic functions; `jacobiSymbol` and `chineseRemainder`
  support modular-arithmetic workflows.

### Background & History

Carl Friedrich Gauss called number theory "the queen of mathematics," and
combinatorics supplies the discrete counting machinery behind probability,
cryptography, and algorithm analysis. Several functions here are genuinely
ancient: the sieve of Eratosthenes dates to c. 240 BCE, and the Chinese
Remainder Theorem appears in Sunzi's _Mathematical Classic_ (3rd–5th century
CE). Euler defined the totient function in 1763; the Möbius function and Möbius
inversion came from August Möbius in 1832. These tools are no museum pieces —
`eulerPhi` and `chineseRemainder` are working components of RSA and modern
public-key cryptography.

import {
  fibonacci,

  eulerPhi,
  chineseRemainder,
} from '@danielsimonjr/mathts-functions';

fibonacci(20); // 6765
primeFactors(360); // [2, 2, 2, 3, 3, 5]
eulerPhi(36); // 12

### Selection (O(n), no full sort)

| Function              | Description                      |
| --------------------- | -------------------------------- |
| `quickSelect(arr, k)` | kth smallest element (0-indexed) |
| `medianSelect(arr)`   | Exact median via quickselect     |
| `minSelect(arr, k)`   | `k` smallest elements            |
| `maxSelect(arr, k)`   | `k` largest elements             |

### Details

- Scalar and small-array overloads are synchronous; the `parallelStat*` family
  takes a `Float64Array`, runs across worker threads, and returns a `Promise`.
- `parallelStatVariance` and `parallelStatStd` accept a `type` argument:
  `'unbiased'` (divides by `n − 1`, the default), `'uncorrected'` (divides by
  `n`), or `'biased'`.
- The selection functions (`quickSelect`, `medianSelect`, `minSelect`,
  `maxSelect`) run in expected **linear** time and avoid sorting the whole
  array — use them instead of `sort` when you need only order statistics.
- `parallelStatMinMax` returns both extremes in a single pass over the data.

### Background & History

Descriptive statistics took its modern shape between the 1880s and 1930s through
the work of Francis Galton, Karl Pearson, and Ronald Fisher. The use of `n − 1`
in the unbiased variance — Bessel's correction — compensates for estimating the
mean from the same sample. The selection routines descend from C. A. R. Hoare's
quickselect (1961), a sibling of quicksort that locates the kth-order statistic
without paying for a full sort.

### Details

- Standalone `*PDF` / `*PMF` / `*CDF` functions evaluate a single point; the

- `ppf` is the inverse CDF (the quantile function): `dist.ppf(0.975)` returns

### Background & History

Poisson distribution (Siméon Poisson, 1837) models rare events; Student's
t-distribution was published by William Gosset in 1908 under the pseudonym
"Student" because his employer, the Guinness brewery, forbade staff from
publishing. The F-distribution is named for Fisher. The information-theoretic
quantities — entropy and the Kullback–Leibler divergence — originate with Claude
Shannon (1948) and Solomon Kullback & Richard Leibler (1951).

### WebGPU-accelerated operations

GPU compute-shader implementations of the core matrix operations. Each runs on
the GPU when a WebGPU device is present and the matrix is large enough to
amortize the dispatch, and falls back transparently to the CPU implementation
otherwise. All four are `async`. The GPU path computes in 32-bit float — use
the standard `multiply` / `transpose` when full f64 precision is required.

| Function          | Description           | Accel  |
| ----------------- | --------------------- | ------ |
| `gpuMatmul(a, b)` | Matrix multiplication | WebGPU |

### Sparse (CSC) routines

`csChol`, `csLu`, `csSpsolve`, `csSqr`, `csCounts`, `csSymperm`, `csAmd`.

### Details

- `det` and `inv` use LU factorisation with partial pivoting; `eigs` uses the
  QR iteration, with a specialised symmetric path for Hermitian inputs.
- `cholesky` requires a symmetric positive-definite matrix and will throw
  otherwise; it is roughly twice as fast as LU when applicable.
- `expm` uses scaling-and-squaring with a Padé approximant — the recommended
  algorithm for the matrix exponential.
- Solving `Ax = b` repeatedly with the same `A` is cheapest via `lup` once
  followed by `lsolve`/`usolve`, rather than forming `inv(A)`.
- Sparse routines accept compressed-sparse-column (`SparseMatrix`) input and
  preserve sparsity through the factorisation.
- For rank-N tensor equivalents — `tensorPinv`, `tensorSolve(A, b)`,
  `tensorKron(a, b)`, `tensorQr`, `tensorSvd`, `tensorLU`, `tensorCholesky`,
  `tensorEig` — see the `@danielsimonjr/mathts-tensor` package. The tensor
  versions accept named `Index` axes and auto-match operands by Index id when
  `axisLabels` are present.

### Background & History

Matrices were systematised by Arthur Cayley and James Joseph Sylvester in the
1850s, though Gaussian elimination is far older — it appears in the Han-dynasty
Chinese text _Nine Chapters on the Mathematical Art_ and was rediscovered by
Gauss. The single most important modern result here is the QR algorithm for
eigenvalues, developed independently by John Francis and Vera Kublanovskaya
around 1961 and still the standard method. The LAPACK-style decompositions —
LU, QR, Cholesky, Schur — are the workhorses on which essentially all numerical
scientific computing rests.

### Details

- Polynomials are represented as coefficient arrays in **descending** degree
  order: `[1, 0, -1]` denotes `x² − 1`.
- `polyval` uses Horner's method, which minimises both operation count and
  rounding error.
- Symbolic functions (`expand`, `factor`, `simplify`, `collect`, …) accept
  either an expression string or an already-parsed AST node and return the
  transformed expression.
- `factor` works over the rationals; it will not introduce irrational or
  complex roots unless they are already present.
- `apart` / `together` are inverses: partial-fraction decomposition versus
  recombination into a single rational expression.
- **WASM acceleration:** `polymul`, `polynomialGCD`, `polynomialLCM`,
  `polynomialQuotient`, and `polynomialRemainder` route to an AssemblyScript WASM
  kernel for coefficient arrays of length ≥ 256 (`WASM_POLY_THRESHOLD`).
  Smaller inputs stay on the JS path where marshal overhead would dominate.
  `discriminant` and `resultant` are tracked for a follow-up slice that
  reuses the new `poly_div_mod_f64` kernel.

### Background & History

Symbolic computation — manipulating expressions as exact algebraic objects
rather than as floating-point numbers — was pioneered by systems such as Macsyma
(MIT, 1968) and Reduce. Horner's method for polynomial evaluation, though named
for William Horner (1819), was known to Chinese mathematician Qin Jiushao in
1247 and even to Isaac Newton. Keeping results symbolic preserves exactness and
human readability: `expand((x+1)^3)` yields a polynomial a reader can verify,
not a numerical approximation.

### Examples

```typescript

polyval([1, 0, -1], 3); // 8  (x² - 1 at x = 3)
factor('x^2 - 1'); // '(x - 1)(x + 1)'
expand('(x + 1)^3'); // 'x^3 + 3*x^2 + 3*x + 1'
```

### Background & History

The CAS layer brings Mathematica- and Maple-style symbolic calculus to MathTS.
Symbolic integration rests on the Risch algorithm (Robert Risch, 1968), which
decides whether an elementary antiderivative exists, supplemented by heuristic
rule sets. The integral transforms have deep roots: the Laplace transform comes
from Pierre-Simon Laplace's work in the 1780s, and the Fourier series from
Joseph Fourier's 1822 _Théorie analytique de la chaleur_. Both share one
purpose — converting calculus problems into algebra. Gröbner bases (Bruno
Buchberger, 1965) play the analogous role for systems of polynomial equations.

## Numerical Integration

| Function                     | Description                            |
| ---------------------------- | -------------------------------------- |
| `trapz(y[, x])`              | Trapezoidal rule on sampled data       |
| `simpson(f, a, b[, n])`      | Simpson's 1/3 rule (`n` even)          |
| `simpsons(f, a, b[, n])`     | Simpson's rule variant (numeric layer) |
| `gaussQuad(f, a, b[, n])`    | Gauss–Legendre quadrature              |
| `romberg(f, a, b[, tol])`    | Romberg integration                    |
| `nintegrate(f, a, b[, tol])` | Adaptive numerical integration         |

### Details

- `trapz` integrates already-sampled data (a `y` array, optionally with matching
  `x` samples); the remaining routines take a callable `f` and evaluate it.
- `simpson` requires an **even** number of subintervals `n`.
- `gaussQuad` with `n` nodes integrates polynomials up to degree `2n − 1`
  exactly — far more accurate per evaluation than equally spaced rules for
  smooth integrands.
- `romberg` and `nintegrate` refine adaptively until a tolerance is met; prefer
  `nintegrate` for integrands with peaks or mild singularities.

### Background & History

Numerical quadrature — literally "squaring," computing an area — predates
calculus itself. The trapezoidal and Simpson rules are Newton–Cotes formulas,
fitting low-degree polynomials through equally spaced points. Gauss–Legendre
quadrature (Carl Friedrich Gauss, 1814) instead chooses the _optimal_ node
positions, doubling the degree of exactness for the same number of evaluations.
Romberg integration (Werner Romberg, 1955) accelerates the trapezoidal rule by
applying Richardson extrapolation to a sequence of refinements.

### Examples

```typescript
import { simpson, gaussQuad, romberg } from '@danielsimonjr/mathts-functions';

simpson(Math.sin, 0, Math.PI, 100); // ~2.0
gaussQuad(Math.sin, 0, Math.PI, 5); // ~2.0
romberg(Math.sin, 0, Math.PI); // ~2.0
```

### Details

- **Interpolation** passes exactly through the data points; **fitting**
  minimises residuals and need not.
- `cubicSpline`, `pchipInterp`, and `pchip` return an _evaluator function_ —
  call it at any query point. `pchip` is monotone-preserving and will not
  introduce overshoot between data points.
- `polyFit` solves a least-squares normal-equation system; `curvefit` fits an
  arbitrary nonlinear model from an initial parameter guess `p0`.
- `griddata` and `rbfInterpolate` handle scattered (non-gridded) data;
  `chebyshevApprox` and `padeApproximant` approximate a known function.
- **WASM acceleration:** `cubicSpline` routes its tridiagonal-solve hot loop
  to an AssemblyScript WASM kernel (Thomas algorithm) when the system has ≥ 1024
  unknowns (`WASM_TRIDIAG_THRESHOLD`). `pchip` and `akima` use analytic
  monotone-cubic slope formulas (Fritsch-Carlson / Akima) with no
  tridiagonal system, so they stay pure JS.

### Background & History

Interpolation tables are ancient — astronomers interpolated planetary positions
long before calculus — but the polynomial theory was formalised by Newton and
Joseph-Louis Lagrange (1795). High-degree polynomial interpolation suffers from
Runge's phenomenon, wild oscillation near the interval ends; cubic splines,
introduced by Isaac Schoenberg in 1946, avoid it by stitching together low-degree
pieces. Curve fitting by least squares is older still: Gauss and Legendre both
developed it around 1805, and it remains the foundation of regression and
experimental data analysis.

### Examples

```typescript
import { cubicSpline, polyFit, lagrangeInterp } from '@danielsimonjr/mathts-functions';

const xs = [0, 1, 2, 3],
  ys = [0, 1, 4, 9];
const spline = cubicSpline(xs, ys);
spline(1.5); // ~2.25
polyFit(xs, ys, 2); // ≈ [1, 0, 0]  (y = x²)
lagrangeInterp(xs, ys, 2.5); // ~6.25
```

### Details

- `findRoot` requires a sign change across the bracket `[a, b]`; it combines the
  guaranteed convergence of bisection with the speed of Brent's method.
- `minimize` / `maximize` find a **local** optimum near the starting point
  `x0`; `globalMinimize` searches a bounded region for a global optimum.
- `linprog` and `quadprog` solve constrained linear and quadratic programs.
- The ODE family ranges from fixed-step (`solveODE`) through adaptive
  (`odeAdaptiveStep`) to `stiffODESolver` for stiff systems where explicit
  methods would require impractically small steps.
- `cond(A)` reports how sensitive a linear solve is to perturbations — a large
  condition number warns that `linsolve` results may be unreliable.

### Background & History

Newton's method (Isaac Newton, 1669; refined by Joseph Raphson) and the
bisection method are the classic root-finders; Richard Brent's 1973 algorithm
combines bracketing safety with superlinear speed and is the modern default.
The Runge–Kutta family for ODEs was developed by Carl Runge and Wilhelm Kutta
around 1900. Optimisation has a sharper birthday: George Dantzig invented the
simplex method for linear programming in 1947, and interior-point methods
followed in the 1980s, opening up large-scale quadratic and convex programming.

### Examples

```typescript

  [
    [1, 0],
    [1, 1],
    [1, 2],
  ],
  [1, 2, 3]
); // [1, 1]
```

## Signal Processing

Every `parallel*` transform dispatches its FFT work to worker threads and
returns a `Promise`: `parallelFFT` / `parallelIFFT` decompose a single large
transform via the four-step (transpose) algorithm into two batches of
independent smaller FFTs; `parallelFFTMagnitude` / `parallelFFTPower`
parallelize the element-wise spectra; `parallelConv` / `parallelXCorr` /
`parallelAutoCorr` run the two forward FFTs concurrently. `spectrogram` and
`fft2d` likewise dispatch their batches of independent FFTs. Small inputs fall
back to the sequential radix-2 implementation on the calling thread.

| `parallelFFTPower(x)`                           | FFT power spectrum                                   | parallel       |

| `parallelAutoCorr(a)`                           | Auto-correlation                                     | parallel       |

| `fft2d(matrix)`                                 | 2D FFT                                               | parallel       |

| `dct(x)` / `idct(X)`                            | Discrete cosine transform / inverse                  | WASM           |

| `highpassFilter(x, fc)`                         | High-pass filter                                     | WASM           |
| `bandpassFilter(x, f1, f2)`                     | Band-pass filter                                     | WASM           |
| `medfilt(x[, window])`                          | Median filter                                        | —              |
| `windowFunction(n, type)`                       | Window functions (Hamming, Hann, …)                  | —              |
| `resample(x, ratio)`                            | Signal resampling                                    | —              |

| `periodogram(x)`                                | Power spectral density estimate                      | WASM           |

### Details

- The `parallel`-marked transforms return a `Promise` and dispatch their FFT
  work to the worker pool above the parallel threshold: `parallelFFT` /
  `parallelIFFT` use a four-step decomposition that splits one transform into
  two batches of independent smaller FFTs; `parallelFFTMagnitude` /
  `parallelFFTPower` parallelize the element-wise spectrum pass; `parallelConv`
  / `parallelXCorr` / `parallelAutoCorr` run the two forward FFTs concurrently;
  `spectrogram` and `fft2d` dispatch their batches of independent FFTs. Below
  the threshold all of them fall back to the sequential radix-2 core.
  `parallelIFFT`, `spectrogram`, and `fft2d` became `async` for this.
- FFT routines are fastest at power-of-two lengths; other lengths use a
  mixed-radix path.
- WASM-marked transforms (`dct`, `dwt`, `spectrogram`, the FIR filters, …) use a
  WebAssembly kernel for inputs above an internal size threshold and fall back
  to the TypeScript implementation otherwise.
- Apply a `windowFunction` (Hamming, Hann, Blackman, …) before an FFT to reduce
  spectral leakage from finite-length signals.
- `spectrogram` gives a time–frequency picture; `periodogram` estimates the
  power spectral density.
- `unwrapPhase` removes the artificial 2π jumps that appear when phase is
  computed with `atan2`.

### Background & History

The Fourier transform — the decomposition of a signal into its constituent
frequencies — comes from Joseph Fourier's 1822 study of heat conduction. For
over a century it was a theoretical tool; the breakthrough was the
**Fast Fourier Transform** of James Cooley and John Tukey (1965), which cut the
cost of an N-point transform from O(N²) to O(N log N). (Gauss had in fact
discovered an equivalent algorithm in 1805, unpublished.) The FFT is now one of
the most-used algorithms in existence — the engine behind digital audio, image
compression, wireless communication, and spectral analysis.

### Examples

```typescript
import { parallelFFT, parallelConv, windowFunction } from '@danielsimonjr/mathts-functions';

const signal = new Float64Array(1024).map((_, i) => Math.sin((2 * Math.PI * i) / 64));
const spectrum = await parallelFFT(signal);
const filtered = await parallelConv(signal, new Float64Array([0.25, 0.5, 0.25]));
```

indispensable in mesh generation, geographic information systems, computer
graphics, and scattered-data interpolation.

## Graph Theory

Algorithms over adjacency-matrix representations.

| Function                           | Description                              |
| ---------------------------------- | ---------------------------------------- |
| `adjacencyMatrix(edges, n)`        | Build adjacency matrix from an edge list |
| `shortestPath(adj, start, end)`    | Dijkstra shortest path (node sequence)   |
| `graphDistance(adj, start, end)`   | Shortest-path length                     |
| `minimumSpanningTree(adj)`         | MST (Prim) → edge list                   |
| `connectedComponents(adj)`         | Connected components                     |
| `stronglyConnectedComponents(adj)` | SCCs (Kosaraju)                          |
| `topologicalSort(adj)`             | Topological order (DAGs)                 |
| `isConnected(adj)`                 | Connectivity test                        |

### Details

- Graphs are represented by an adjacency matrix; build one from an edge list
  with `adjacencyMatrix(edges, n)`.
- `shortestPath` uses Dijkstra's algorithm and returns the node sequence;
  `graphDistance` returns only the total path length.
- `topologicalSort` is defined for directed acyclic graphs — a cycle makes a
  topological order impossible.
- `stronglyConnectedComponents` (Kosaraju's algorithm) applies to directed
  graphs; `connectedComponents` to undirected ones.

### Background & History

Graph theory began with a recreational puzzle: in 1736 Leonhard Euler proved
that no walk could cross each of the seven bridges of Königsberg exactly once,
founding the field in the process. Its algorithmic core is much more recent —
Edsger Dijkstra published his shortest-path algorithm in 1959, and the
minimum-spanning-tree algorithms span Otakar Borůvka (1926), Joseph Kruskal
(1956), and Robert Prim (1957). These algorithms underpin routing, network
design, dependency resolution, and scheduling.

### Examples

```typescript
import {
  adjacencyMatrix,
  shortestPath,
  minimumSpanningTree,
} from '@danielsimonjr/mathts-functions';

const adj = adjacencyMatrix(
  [
    [0, 1],
    [1, 2],
    [0, 2],
  ],
  3
);
shortestPath(adj, 0, 2); // [0, 2]
minimumSpanningTree(adj); // MST edge list
```

## Hypothesis Tests

All return structured result objects.

| Function                                   | Returns             | Description           |
| ------------------------------------------ | ------------------- | --------------------- |
| `studentTTest(sample1[, sample2])`         | `TTestResult`       | One/two-sample t-test |
| `chiSquareTest(observed, expected)`        | `ChiSquareResult`   | Chi-square test       |
| `anova(groups)`                            | `AnovaResult`       | One-way ANOVA         |
| `kolmogorovSmirnovTest(sample[, sample2])` | `KSTestResult`      | K-S test              |
| `mannWhitneyTest(sample1, sample2)`        | `MannWhitneyResult` | Mann–Whitney U test   |
| `shapiroWilkTest(sample)`                  | `ShapiroWilkResult` | Normality test        |
| `principalComponentAnalysis(data[, k])`    | `PCAResult`         | PCA                   |

### Details

- Each test returns a structured object containing at minimum the test
  statistic and a p-value, plus test-specific fields (degrees of freedom,
  significance flag, …).
- The **parametric** tests (`studentTTest`, `anova`, `chiSquareTest`) assume an
  underlying distribution; the **nonparametric** tests (`mannWhitneyTest`,
  `kolmogorovSmirnovTest`) do not and are robust to non-normal data.
- `shapiroWilkTest` checks a sample for normality — useful for deciding between
  parametric and nonparametric procedures.
- `principalComponentAnalysis` returns the principal components and their
  explained-variance ratios; pass `k` to keep only the top components.

### Background & History

Statistical hypothesis testing was built in the 1920s–30s by two competing
schools: Ronald Fisher's significance testing and the decision-theoretic
framework of Jerzy Neyman and Egon Pearson. The t-test was published by William
Gosset ("Student") in 1908; Fisher introduced the analysis of variance. The
nonparametric tests — Mann–Whitney (1947), Kolmogorov–Smirnov — were developed
to draw conclusions without assuming a normal distribution. Principal component
analysis goes back to Karl Pearson (1901) and Harold Hotelling (1933).

### Examples

```typescript
import { studentTTest, anova } from '@danielsimonjr/mathts-functions';

studentTTest([2.1, 2.5, 2.3], [3.1, 3.5, 2.9]);
// { t, pValue, degreesOfFreedom, significant }
```

## Set Operations

| Function                 | Description                                                       | Types | Accel |
| ------------------------ | ----------------------------------------------------------------- | ----- | ----- |
| `setUnion(a, b)`         | Union of two multisets                                            | Array | —     |
| `setIntersect(a, b)`     | Intersection of two multisets                                     | Array | —     |
| `setDifference(a, b)`    | Elements of `a` not in `b` (multiset difference)                  | Array | —     |
| `setSymDifference(a, b)` | Symmetric difference of two multisets                             | Array | —     |
| `setCartesian(a, b)`     | Cartesian product — all ordered pairs                             | Array | —     |
| `setPowerset(a)`         | All subsets ordered by size                                       | Array | —     |

| `setMultiplicity(e, a)`  | Count occurrences of element `e` in multiset `a`                  | Array | —     |

### Details

- All ten functions (`setUnion`, `setIntersect`, `setDifference`,
  `setSymDifference`, `setCartesian`, `setPowerset`, `setDistinct`,
  `setMultiplicity`, `setIsSubset`, `setSize`) are **typed-layer**
  implementations; multi-dimensional input arrays are flattened before the
  operation.
- Operations respect **multiset semantics**: duplicate elements count
  independently. `setMultiplicity` returns the count of a value; `setDistinct`
  removes duplicates; `setIsSubset` checks with multiplicity.
- `setPowerset` produces `2ⁿ` subsets — guard the input size, as it grows
  exponentially.
- `setCartesian` returns all ordered pairs `[x, y]`; `setSize` with `true`
  reports the count of unique values only.

### Background & History

Set theory was created almost single-handedly by Georg Cantor in the 1870s and
became, through the Zermelo–Fraenkel axioms, the standard foundation of modern
mathematics. The operations here are the concrete, computational face of that
theory — they support combinatorial enumeration, relational queries, and the
canonicalisation steps inside symbolic computation.

### Examples

```typescript

setUnion([1, 2, 3], [2, 3, 4]); // [1, 2, 3, 4]
setIntersect([1, 2, 3], [2, 3, 4]); // [2, 3]
setPowerset([1, 2]); // [[], [1], [2], [1, 2]]
```

## Units

| Function                 | Description                                |
| ------------------------ | ------------------------------------------ |
| `unit(value, unit)`      | Construct a `Unit`                         |
| `createUnit(defs)`       | Define custom units (`factory_createUnit`) |
| `to(unit, target)`       | Convert between units                      |
| `toBest(unit)`           | Convert to the best-fitting prefix         |
| `splitUnit(unit, parts)` | Split a unit into components               |

### Details

- A `Unit` couples a numeric value with a physical dimension; `to` converts only
  between dimensionally compatible units and throws otherwise.
- `toBest` selects the metric prefix that yields the most readable magnitude
  (e.g. `1500 m → 1.5 km`).
- `createUnit` registers derived or custom units built from existing ones.
- `splitUnit` decomposes a quantity into mixed parts (e.g. a length into feet
  and inches).

### Background & History

Coherent systems of units descend from the metric system, adopted in France in
1795, and the International System of Units (SI), established in 1960.
Carrying units through a computation as first-class data turns dimensional
analysis into an automatic check — catching exactly the class of mistake behind
the 1999 loss of NASA's Mars Climate Orbiter, where pound-force and newton
quantities were silently mixed.

### Examples

```typescript
import { unit, to } from '@danielsimonjr/mathts-functions';

const d = unit(100, 'km');
to(d, 'mile'); // ≈ 62.137 mile
to(unit(90, 'km/h'), 'm/s'); // 25 m/s
```

## Complex Number Utilities

| Function  | Description                                           | Types                                     | Accel |
| --------- | ----------------------------------------------------- | ----------------------------------------- | ----- |
| `arg(z)`  | Phase angle in radians — `atan2(im, re)`              | number, bigint, BigNumber, Complex, Array | —     |
| `conj(z)` | Complex conjugate — negates the imaginary part        | number, bigint, BigNumber, Complex, Array | —     |
| `re(z)`   | Real part — identity for real types, `re` for Complex | number, bigint, BigNumber, Complex, Array | —     |
| `im(z)`   | Imaginary part — 0 for real types, `im` for Complex   | number, bigint, BigNumber, Complex, Array | —     |

### Details

- All four functions (`arg`, `conj`, `re`, `im`) are **typed-layer**
  implementations with `Array` elementwise dispatch.
- `arg` returns the phase (argument) in radians; for positive reals the result is
  `0`, for negative reals `π`. Range for `Complex` inputs: `(-π, π]`.
- `conj` negates the imaginary part; for real types (`number`, `bigint`,
  `BigNumber`) it returns the value unchanged.
- `re` and `im` extract the Cartesian components; for real types `re` returns the
  value itself and `im` returns `0`.

### Background & History

Complex numbers were treated with deep suspicion for centuries — Rafael
Bombelli first manipulated them in 1572, and the term "imaginary" itself records
that distrust. They were made rigorous by the geometric interpretation of
Caspar Wessel, Jean-Robert Argand, and Gauss around 1800. Today they are
indispensable: AC circuit analysis, control theory, quantum mechanics, and
signal processing all rely on the complex plane.

### Examples

```typescript
import { arg, conj, re, im } from '@danielsimonjr/mathts-functions';
import { Complex } from '@danielsimonjr/mathts-core';

const z = new Complex(3, 4);
re(z); // 3
im(z); // 4
arg(z); // ~0.9273  (atan2(4, 3))
conj(z); // Complex(3, -4)
```

## Type Conversion

Convert a value into a specific numeric or container type.

| Function            | Description                                   |
| ------------------- | --------------------------------------------- |
| `number(x)`         | Convert to a primitive `number`               |
| `bigint(x)`         | Convert to a `bigint`                         |
| `bignumber(x)`      | Convert to an arbitrary-precision `BigNumber` |
| `fraction(x)`       | Convert to an exact `Fraction`                |
| `complex(re[, im])` | Convert to / construct a `Complex`            |
| `matrix(data)`      | Convert to a dense `DenseMatrix`              |
| `sparse(data)`      | Convert to a `SparseMatrix` (CSC storage)     |
| `string(x)`         | Convert to a `string`                         |
| `boolean(x)`        | Convert to a `boolean`                        |

The factory-layer `numeric(x, type)` (see below) is a single-entry dispatcher
over the same conversions.

### Details

- Conversions to `BigNumber` and `Fraction` are **exact** when the source
  permits; converting _out_ of them (`number`) is lossy and may round.
- Convert from a string for exactness — `bignumber('0.1')` is the true value
  one-tenth, whereas `bignumber(0.1)` first inherits the binary rounding error
  of the literal `0.1`.
- `matrix` produces dense storage; `sparse` produces compressed-sparse-column
  storage suited to matrices that are mostly zero.

### Background & History

A library that supports several numeric representations needs an explicit,
visible boundary between them. These functions are that boundary. The crucial
distinction is between the **exact** types — `Fraction` and `BigNumber`, which
carry no rounding error — and the fast, fixed-width IEEE-754 `number`. Making
each crossing an explicit call keeps a programmer in deliberate control of when
precision is traded for speed.

### Examples

```typescript
import { fraction, bignumber, complex } from '@danielsimonjr/mathts-functions';

fraction(0.25); // Fraction(1, 4)
bignumber('0.1'); // exact BigNumber 0.1 (no binary rounding error)
complex(2, 3); // Complex(2, 3)
```

## Expression Evaluation

| Function                  | Description                                                                      |
| ------------------------- | -------------------------------------------------------------------------------- |
| `evaluate(expr[, scope])` | Evaluate an expression string                                                    |
| `compileExpr(expr)`       | Compile once, evaluate many                                                      |
| `parse(expr)`             | Parse an expression into an AST node                                             |
| `parser()`                | Create a stateful parser with a scope retained across calls                      |
| `reviver(key, value)`     | `JSON.parse` reviver — restores `Complex`, `Fraction`, non-finite numbers        |
| `replacer(key, value)`    | `JSON.stringify` replacer — serialises `Complex`, `Fraction`, non-finite numbers |

### Details

- `evaluate` parses and evaluates in one call; `compileExpr` compiles once and
  is far faster when the same expression is evaluated repeatedly with different
  variable bindings.
- `parse` returns the abstract syntax tree as a `Node`, which can be inspected,
  transformed, or fed to the symbolic-algebra functions.
- `parser()` creates a stateful evaluator that retains variable and function
  definitions across calls.
- Property and method access inside expressions is routed through sandbox
  helpers — a deliberate security boundary so that user-supplied formulas cannot
  reach arbitrary JavaScript.

### Background & History

A safe expression evaluator lets an application accept user-entered formulas
without resorting to JavaScript's `eval`, which would expose the entire runtime.
This is the same design that distinguishes mathjs from naive calculators: the
parser builds an explicit syntax tree, and every member access is checked
against an allow-list. The result is a feature that doubles as a security
boundary.

### Examples

```typescript
import { evaluate, compileExpr } from '@danielsimonjr/mathts-functions';

evaluate('2 + 3 * 4'); // 14
evaluate('pi * r^2', { r: 5 }); // 78.5398...

const fn = compileExpr('x^2 + 2*x + 1');
fn.evaluate({ x: 3 }); // 16
```

## Parallel Execution Model

### Details

- `Float64Array` (and large-matrix) inputs to the typed functions return a
  `Promise` of the result value directly — `Promise<Float64Array>` for
  element-wise transforms, `Promise<number>` for reductions. Await the call.
- The worker pool is created lazily on first use. `initializePool()`,
  `getComputePool()`, and `terminatePool()` give explicit lifecycle control —
  call `terminatePool()` to release worker threads, for example before process
  exit.
- Small inputs run sequentially even on a `parallel`-marked function; the
  library dispatches to workers only when the array is large enough for the
  work to outweigh the dispatch overhead, and only once the pool has been
  initialized — otherwise it falls back to a synchronous in-thread path.
- The lower-level `ComputePool` API (`computePool.add`, `.matmul`,
  `.applyKernel`, …) returns a `ParallelResult` wrapper that carries `.result`,
  `.duration` (elapsed milliseconds), `.chunks` (number of work chunks), and
  `.parallelized` (whether worker threads were actually used).

### Background & History

MathTS is "parallel-first": rather than treating multi-threading as an opt-in
optimisation, array transforms are designed from the start to fan out across
Web Worker threads. This reflects the hardware reality that single-core clock
speeds plateaued in the mid-2000s and that performance gains now come from
parallelism. The worker-pool pattern — a fixed set of reusable worker threads
fed by a task queue — is the standard way to exploit those cores without paying
thread-creation costs on every call.

### Examples

```typescript
import { add, initializePool, terminatePool } from '@danielsimonjr/mathts-functions';

await initializePool();
const sum = await add(new Float64Array([1, 2, 3]), new Float64Array([4, 5, 6]));
// sum → Float64Array([5, 7, 9])
await terminatePool();
```
